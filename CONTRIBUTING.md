# Як здавати лабораторні роботи

Цей документ описує процес здачі. Він однаковий для всіх робіт курсу, тож
прочитайте його один раз уважно — далі повертатиметесь лише за командами.

## 1. Одноразове налаштування

Зробіть fork репозиторію курсу (кнопка **Fork** угорі сторінки), потім:

```bash
git clone https://github.com/ВАШ_ЛОГІН/CS1232026.git
cd CS1232026
git remote add upstream https://github.com/yevhentolstoluzkyi-code/CS1232026.git
git remote -v        # origin — ваш форк, upstream — репозиторій курсу
```

Перевірте, що Git знає, хто ви. Ці дані назавжди потраплять у кожен ваш коміт:

```bash
git config --global user.name  "Прізвище Ім'я"
git config --global user.email "ваша.пошта@example.com"
```

## 2. Для кожної роботи

```bash
git switch main
git fetch upstream
git rebase upstream/main          # підтягнути чужі роботи, що вже влилися
git switch -c lab03-shevchenko    # гілка під конкретну роботу
```

Працюйте **тільки** в каталозі `labNN/submissions/ГРУПА_Прізвище/`. Файли поза
ним ваш pull request змінювати не повинен.

Комітьте невеликими логічними порціями. Повідомлення коміту пояснює **навіщо**,
а не «що» — що саме змінилося, видно з diff:

```
добре:  ЛР3: перевірка результату fopen перед читанням
погано: update, fix, дороблено, final version 2
```

## 3. Відправлення

```bash
git push -u origin lab03-shevchenko
```

Далі на GitHub відкрийте pull request зі своєї гілки в `main` репозиторію курсу.

- **Заголовок:** `ЛР3: Шевченко, КІ-31`
- **Опис:** що зроблено, у якому середовищі, що виявилося найскладнішим.

## 4. Рев'ю

Рев'юер залишає зауваження до конкретних рядків. Від вас очікується:

- відповісти по суті — погодитися й виправити або обґрунтувати своє рішення;
- виправлення додавати **новими комітами в ту саму гілку** (`git push` оновить
  PR автоматично, створювати новий не потрібно);
- не робити `push --force` у гілку, яку вже читає рев'юер.

Робота зарахована, коли PR влито в `main`.

## 5. Чого в комітах бути не повинно

Ці файли або великі, або генеровані, або особисті — і жодному репозиторію не
потрібні:

```
*.o *.a *.so *.exe
minigrep sum             # зібрані бінарники
target/                  # результати збірки Rust
.vscode/ .idea/ .DS_Store
*.swp *~
```

Перевірити, що зайвого немає, можна перед відправленням:

```bash
git status
git diff --stat upstream/main...HEAD
```

## 6. Типові причини повернення роботи на доопрацювання

- Змінено файли поза власним каталогом.
- У коміти потрапили бінарники або `target/`.
- Історія з одного коміту «зробив усе» замість кількох логічних.
- Код не збирається на чистій машині: бракує `Makefile`, `Cargo.toml` або
  залежність встановлена лише у вас.
- Автор не може пояснити, що робить рядок, який він надіслав.
